# Part 1/8

# Philosophy, Positioning & User Experience

---

# 1. Purpose

Este documento define la especificación funcional completa del **GitHub Profile README** de Fran Ramirez.

No es el README definitivo.

Es el documento de referencia desde el que se construirán:

```text id="gprm001"
README.md
README.es.md
```

Toda decisión relacionada con:

* contenido,
* estructura,
* diseño,
* iconografía,
* lenguaje,
* accesibilidad,
* mantenimiento,
* evolución,

deberá quedar documentada aquí antes de implementarse.

Este documento constituye la **Single Source of Truth** del Profile README.

---

# 2. Vision

El objetivo no consiste en crear un README atractivo.

El objetivo consiste en diseñar una **landing page profesional** que represente de forma fiel la identidad técnica de Fran Ramirez.

El Profile README deberá transmitir:

* claridad;
* credibilidad;
* calidad;
* madurez técnica;
* capacidad de aprendizaje;
* criterio de ingeniería.

No deberá parecer un currículum.

No deberá parecer una lista de tecnologías.

No deberá parecer una colección de badges.

Deberá parecer la página principal de un ingeniero de software.

---

# 3. Mission

El README deberá responder, en menos de un minuto, a las preguntas que cualquier visitante formula de manera inconsciente al llegar a un perfil técnico.

```text id="gprm002"
¿Quién es?

↓

¿Qué tipo de software desarrolla?

↓

¿Tiene experiencia demostrable?

↓

¿Qué proyectos merece la pena abrir?

↓

¿Cómo trabaja?

↓

¿Quiero contactar con esta persona?
```

Si el visitante necesita buscar estas respuestas, el README habrá fallado.

---

# 4. Long-Term Objective

Este Profile README deberá mantenerse vigente durante al menos:

```text id="gprm003"
2–3 años
```

La arquitectura será estable.

Los cambios futuros deberán afectar principalmente al contenido.

No a la estructura.

---

# 5. Design Philosophy

El diseño seguirá cinco principios fundamentales.

---

## Principle 1

### Simplicity over Decoration

Cada elemento deberá justificar su existencia.

No se añadirán componentes únicamente porque sean populares en GitHub.

---

## Principle 2

### Content over Effects

El contenido tendrá prioridad absoluta sobre:

* animaciones;
* badges;
* widgets;
* gráficos.

---

## Principle 3

### Engineering over Marketing

El README venderá evidencia.

No promesas.

Cada afirmación deberá estar respaldada por:

* proyectos;
* documentación;
* arquitectura;
* código.

---

## Principle 4

### Timeless Design

Se evitarán tendencias visuales pasajeras.

El objetivo es que el README siga pareciendo moderno dentro de varios años.

---

## Principle 5

### Professional Minimalism

Cada sección deberá transmitir más información utilizando menos elementos visuales.

La densidad de información deberá ser alta.

La densidad visual deberá ser baja.

---

# 48. Purpose

Después del Hero, el visitante ya conoce:

* quién es Fran;
* cuál es su posicionamiento;
* qué tipo de software desarrolla.

La misión de esta sección consiste en responder una única pregunta:

```text id="about001"
¿Por qué debería seguir explorando este perfil?
```

No pretende sustituir al currículum.

No pretende contar toda la trayectoria profesional.

Pretende proporcionar el contexto necesario para interpretar correctamente el resto del portfolio.

---

# 49. Communication Goals

La sección **About Me** deberá conseguir cinco objetivos.

1. Humanizar el perfil.
2. Explicar la evolución profesional.
3. Presentar la forma de trabajar.
4. Introducir los proyectos destacados.
5. Generar credibilidad.

Todo ello utilizando menos de:

```text id="about002"
180 palabras
```

---

# 50. Editorial Philosophy

El About deberá construirse sobre hechos demostrables.

No sobre declaraciones genéricas.

Ejemplo incorrecto:

> Passionate developer.

Ejemplo correcto:

> I enjoy designing maintainable backend systems where architecture, documentation and automation evolve together.

La segunda afirmación puede comprobarse abriendo NovaCoquinaria o Aula Robótica.

---

# 51. Core Narrative

Toda la narrativa girará alrededor de una única idea.

```text id="about003"
Software engineering is more than writing code.
It is designing systems that remain understandable, maintainable and useful over time.
```

Esta idea conecta todos los proyectos principales.

```text id="about004"

↓
```

# 53. Background

El objetivo no consiste en contar veinte años de trayectoria profesional.

Solo aportar el contexto suficiente para comprender el perfil actual.

Deberá explicarse que:

* existe una trayectoria previa;
* esa experiencia ha fortalecido capacidades de comunicación, liderazgo y gestión;
* actualmente el foco profesional está en el desarrollo de software.

No deberán aparecer:

* cargos antiguos;
* organizaciones;
* cronologías completas;
* detalles irrelevantes para un recruiter técnico.

---

# 54. Transition

La transición constituye una de las fortalezas del perfil.

No deberá ocultarse.

Tampoco dramatizarse.

El mensaje será sencillo.

Ejemplo conceptual:

> Después de una larga experiencia gestionando proyectos, decidí orientar mi carrera hacia el desarrollo de software para construir directamente los productos tecnológicos que durante años había ayudado a coordinar.

La redacción definitiva se realizará más adelante.

El foco actual será:

* backend;
* full stack;

* IA aplicada.

* automatización para reducir trabajo repetitivo;
