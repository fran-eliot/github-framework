# Part 1/6

# Visual Identity Philosophy

---

# 1. Purpose

Este documento define la identidad visual del ecosistema GitHub de Fran Ramirez.

No describe únicamente el banner del Profile README.

Define el sistema gráfico que utilizarán:

* GitHub Profile
* NovaCoquinaria
* OnlyFilm
* Aula Robótica
* Cognitiva AI
* Dental Clinic
* futuros proyectos estratégicos

El objetivo es construir una identidad reconocible y coherente.

---

# 2. Vision

El sistema visual deberá transmitir la misma sensación que los proyectos.

No buscará impresionar mediante efectos.

Buscará comunicar:

* ingeniería;
* claridad;
* calidad;
* simplicidad;
* profesionalidad.

La identidad visual deberá sentirse como una extensión natural de la arquitectura de software.

---

# 3. Design Goals

La identidad deberá cumplir simultáneamente los siguientes objetivos.

* Ser reconocible.
* Ser elegante.
* Ser atemporal.
* Funcionar en modo claro y oscuro.
* Escalar desde un banner hasta una imagen social.
* Reutilizar componentes gráficos.
* Requerir poco mantenimiento.

---

# 4. Brand Personality

La identidad visual reflejará exactamente los atributos definidos en `01_BRAND.md`.

| Attribute    | Visual Interpretation              |
| ------------ | ---------------------------------- |
| Professional | Composición limpia                 |
| Technical    | Geometría y estructura             |
| Curious      | Detalles sutiles                   |
| Pragmatic    | Ausencia de decoración innecesaria |
| Innovative   | Estilo contemporáneo               |
| Humble       | Minimalismo                        |
| Reliable     | Consistencia                       |

---

# 5. Core Principle

La identidad visual deberá responder a una única idea.

```text id="banner001"
Software Engineering over Graphic Design.
```

El diseño deberá estar al servicio del contenido.

Nunca al revés.

---

# 6. Inspiration

La inspiración procederá de productos tecnológicos con una identidad muy cuidada.

Ejemplos.

* GitHub
* Stripe
* Vercel
* Linear
* JetBrains
* Grafana
* HashiCorp

No se copiarán estilos.

Solo principios.

---

# 7. Emotional Response

Al ver el perfil por primera vez el visitante debería pensar:

```text id="banner002"
Este perfil parece muy cuidado.

↓

Da sensación de ingeniería.

↓

Quiero seguir leyendo.
```

No:

```text id="banner003"
Qué banner más llamativo.
```

El banner nunca debe eclipsar el contenido.

---

# 8. Design Language

El lenguaje visual será:

* minimalista;
* geométrico;
* modular;
* limpio;
* tecnológico.

Nunca:

* futurista;
* agresivo;
* recargado;
* oscuro por defecto.

---

# 9. Visual Keywords

Las palabras clave del sistema serán:

```text id="banner004"
Grid

Structure

Precision

Space

Flow

Connections
```

Estas ideas aparecerán repetidamente en todos los activos gráficos.

---

# 10. Anti-Keywords

Quedan descartados:

```text id="banner005"
Cyberpunk

Neon

Gaming

Sci-Fi

Comic

Anime

Glassmorphism extremo

3D exagerado
```

No representan la identidad profesional definida.

---

# 11. Target Audience

El sistema visual está diseñado para:

* recruiters;
* Tech Leads;
* Software Engineers;
* Engineering Managers.

No pretende atraer mediante tendencias de diseño.

Pretende generar confianza.

---

# 12. Timelessness

Toda decisión gráfica deberá responder a la pregunta:

```text id="banner006"
¿Seguirá pareciendo profesional dentro de cinco años?
```

Si la respuesta es dudosa, deberá descartarse.

---

# 13. Visual Hierarchy

La identidad siempre seguirá esta prioridad.

```text id="banner007"
Contenido

↓

Tipografía

↓

Espacio

↓

Color

↓

Elementos gráficos
```

Nunca al revés.

---

# 14. Identity System

El sistema estará compuesto por:

* Banner principal.
* Banner para proyectos.
* Social Preview.
* Paleta cromática.
* Tipografía.
* Iconografía.
* Componentes gráficos.
* Espaciado.

Cada elemento deberá poder reutilizarse.

---

# 15. Consistency Rules

Todos los proyectos estratégicos deberán compartir:

* mismo lenguaje visual;
* misma composición;
* misma paleta;
* mismo estilo tipográfico;
* misma filosofía.

Cada proyecto podrá tener pequeños elementos distintivos, pero nunca romper la identidad global.

---

# 16. Evolution Strategy

La identidad está diseñada para evolucionar.

Cambiarán:

* proyectos;
* tecnologías;
* mensajes.

No cambiarán:

* principios visuales;
* estructura;
* coherencia.

---

# 17. Success Criteria

El sistema visual será exitoso cuando:

* el visitante identifique rápidamente una imagen profesional;
* exista coherencia entre todos los repositorios;
* el diseño no distraiga del contenido;
* los activos gráficos puedan mantenerse fácilmente.

---

# 18. Part 1 Conclusions

La identidad visual del ecosistema GitHub de Fran Ramirez no pretende destacar por ser espectacular.

Pretende destacar por ser **coherente, elegante y técnicamente consistente**.

El diseño deberá reforzar la misma idea que transmiten los proyectos:

> la calidad nace de una buena arquitectura, no de una mayor complejidad.

# 06 - BANNER

# Part 2/6

# Design Language & Visual System

---

# 19. Purpose

Esta sección define el lenguaje visual que utilizarán todos los banners del ecosistema GitHub.

No especifica un banner concreto.

Define las reglas que deberán respetar todos los futuros diseños.

El objetivo consiste en construir una identidad consistente, reconocible y fácilmente ampliable.

---

# 20. Design Philosophy

La identidad gráfica deberá comportarse igual que una buena arquitectura de software.

Será:

* modular;
* reutilizable;
* consistente;
* sencilla de mantener;
* preparada para evolucionar.

Cada decisión visual deberá poder justificarse.

---

# 21. Visual Metaphor

El sistema utilizará una única metáfora visual.

```text id="design001"
Engineering as Structure
```

No representaremos:

* código;
* pantallas;
* teclados;
* ordenadores.

Representaremos:

* estructura;
* conexiones;
* organización;
* relaciones;
* capas.

La ingeniería del software será una idea abstracta, no una ilustración literal.

---

# 22. Graphic Language

Todo elemento gráfico deberá pertenecer a una de estas familias.

### Grid

Representa:

* organización;
* orden;
* arquitectura.

---

### Connections

Representa:

* relaciones;
* comunicación;
* integración.

---

### Layers

Representa:

* arquitectura multicapa;
* separación de responsabilidades.

---

### Nodes

Representa:

* conocimiento;
* sistemas distribuidos;
* datos.

---

### Flow

Representa:

* evolución;
* automatización;
* pipelines.

---

# 23. Visual Composition

Todos los banners compartirán la misma estructura.

```text id="design002"
Background Pattern

↓

Project Name

↓

Professional Tagline

↓

Optional Accent Element
```

No existirán composiciones distintas según el proyecto.

---

# 24. Geometry

El lenguaje gráfico estará basado en:

* líneas;
* rectángulos;
* cuadrículas;
* círculos discretos;
* conexiones.

Nunca en ilustraciones figurativas.

---

# 25. Symmetry

La composición deberá transmitir equilibrio.

No necesariamente simetría perfecta.

El peso visual deberá distribuirse de forma uniforme.

---

# 26. White Space

El espacio vacío constituye un elemento estructural.

Nunca deberá rellenarse simplemente porque exista espacio disponible.

La respiración visual es parte de la identidad.

---

# 27. Visual Rhythm

La composición seguirá un ritmo constante.

No habrá zonas extremadamente densas junto a otras completamente vacías.

La distribución visual deberá recordar a una buena maquetación editorial.

---

# 28. Pattern System

El fondo utilizará patrones geométricos muy sutiles.

Nunca texturas.

Nunca fotografías.

Nunca degradados excesivos.

---

# 29. Pattern Library

Los patrones base serán reutilizables.

Ejemplos.

### Grid

Para proyectos de arquitectura.

---

### Graph

Para conocimiento e IA.

---

### Pipeline

Para automatización.

---

### Layered Blocks

Para backend.

---

### Network

Para sistemas distribuidos.

---

# 30. Pattern Intensity

Los patrones deberán permanecer siempre en segundo plano.

El visitante no deberá percibirlos inmediatamente.

Solo contribuirán a generar profundidad.

---

# 31. Visual Density

El sistema evitará:

* fondos completamente vacíos;
* fondos excesivamente complejos.

El equilibrio será el objetivo principal.

---

# 32. Borders

No se utilizarán marcos decorativos.

Los límites del banner serán limpios.

---

# 33. Shadows

Las sombras serán mínimas.

Solo cuando mejoren la legibilidad.

Nunca como efecto decorativo.

---

# 34. Effects

Quedan permitidos únicamente:

* ligeras transparencias;
* opacidades;
* degradados suaves;
* desenfoques muy discretos.

Quedan descartados:

* glow;
* neón;
* reflejos;
* biseles;
* efectos metálicos.

---

# 35. Motion Philosophy

El banner será completamente estático.

No dependerá de animaciones.

La identidad deberá funcionar incluso como imagen impresa.

---

# 36. Visual Balance

Cada banner deberá responder positivamente a esta pregunta.

```text id="design003"
¿Parece diseñado por un ingeniero?
```

No:

```text id="design004"
¿Parece diseñado por un artista digital?
```

El objetivo no es competir con el diseño gráfico.

Es reforzar una identidad técnica.

---

# 37. Project Differentiation

Cada proyecto utilizará un patrón secundario distinto.

| Project        | Visual Motif            |
| -------------- | ----------------------- |
| GitHub Profile | Grid + Connections      |
| NovaCoquinaria | Knowledge Graph         |
| OnlyFilm       | Layered Architecture    |
| Aula Robótica  | Network & Collaboration |
| Cognitiva AI   | Nodes & Data Flow       |
| Dental Clinic  | Structured Modules      |

Todos compartirán la misma composición general.

---

# 38. Scalability

Todos los elementos deberán escalar correctamente.

El mismo sistema permitirá generar:

* banner GitHub;
* Social Preview;
* Open Graph Image;
* cabeceras de documentación;
* imágenes para artículos técnicos.

---

# 39. Brand Recognition

La identidad deberá ser reconocible incluso sin leer el nombre del proyecto.

La repetición de:

* composición;
* patrones;
* tipografía;
* espaciado;

será el principal mecanismo de reconocimiento.

---

# 40. Accessibility

Los patrones nunca deberán reducir la legibilidad del texto.

Todo elemento decorativo permanecerá por debajo del contenido.

---

# 41. Dark & Light Mode

El sistema deberá funcionar de forma equivalente en:

* modo claro;
* modo oscuro.

No existirán dos identidades distintas.

Solo dos adaptaciones cromáticas.

---

# 42. Reusability

Todo componente gráfico deberá poder reutilizarse.

No se diseñarán elementos exclusivos para un único banner salvo el nombre del proyecto y su motivo secundario.

---

# 43. Anti-Patterns

No utilizar:

* fotografías;
* renders 3D;
* ilustraciones humanas;
* mascotas;
* iconografía tecnológica genérica;
* pantallas de código;
* logos de tecnologías;
* fondos con texto.

El banner no debe explicar el proyecto.

Debe representar su identidad.

---

# 44. Design Quality Gates

Antes de aprobar un diseño deberán verificarse:

* [ ] Mantiene la composición oficial.
* [ ] Utiliza un patrón permitido.
* [ ] El texto es claramente legible.
* [ ] No depende de efectos visuales.
* [ ] Funciona en claro y oscuro.
* [ ] Puede reutilizarse en otros formatos.
* [ ] Refuerza la identidad de ingeniería.

---

# 45. Evolution Strategy

El sistema visual está preparado para incorporar nuevos proyectos.

Solo será necesario definir:

* un motivo secundario;
* un color de acento;
* el nombre del proyecto.

Todo lo demás permanecerá estable.

---

# 46. Part 2 Conclusions

El sistema visual no se basará en banners independientes.

Se construirá como una **familia de componentes gráficos** que compartirán una misma arquitectura visual.

Cada proyecto tendrá personalidad propia, pero todos formarán parte de una identidad común basada en estructura, precisión y simplicidad.

---

# 06 - BANNER

# Part 3/6

# Color System, Typography & Composition

---

# 47. Purpose

Esta sección define el sistema visual base sobre el que se construirán todos los banners del ecosistema GitHub.

Su objetivo consiste en garantizar:

* coherencia;
* legibilidad;
* accesibilidad;
* reutilización.

No se trata de elegir "colores bonitos".

Se trata de construir una identidad visual duradera.

---

# 48. Design Philosophy

El sistema visual seguirá una regla fundamental.

```text id="visual001"
Color supports content.
Content never depends on color.
```

El color reforzará la identidad.

Nunca será el elemento principal.

---

# 49. Visual Hierarchy

La importancia visual seguirá siempre este orden.

```text id="visual002"
Project Name

↓

Tagline

↓

Pattern

↓

Accent Color
```

El visitante deberá leer primero.

Después observar.

Nunca al contrario.

---

# 50. Color Strategy

La identidad utilizará una paleta neutra.

Los colores de acento únicamente diferenciarán proyectos.

El sistema nunca dependerá de colores intensos.

---

# 51. Base Palette

La paleta principal estará formada por:

### Neutral White

Fondos claros.

---

### Neutral Black

Fondos oscuros.

---

### Gray Scale

Jerarquía tipográfica.

Separadores.

Patrones.

Líneas.

---

Esta paleta permanecerá estable.

---

# 52. Accent Philosophy

Cada proyecto tendrá un único color principal.

Nunca dos.

Nunca tres.

El color deberá actuar únicamente como firma visual.

---

# 53. Proposed Accent Colors

## GitHub Profile

Azul profundo.

Representa:

* estabilidad;
* ingeniería;
* confianza.

---

## NovaCoquinaria

Verde azulado (teal).

Representa:

* conocimiento;
* organización;
* crecimiento.

No se utilizará verde culinario.

---

## OnlyFilm

Azul acero.

Representa:

* backend;
* arquitectura;
* calidad.

No rojo cinematográfico.

---

## Aula Robótica

Turquesa.

Representa:

* colaboración;
* tiempo real;
* sistemas.

---

## Cognitiva AI

Violeta discreto.

Representa:

* inteligencia;
* análisis;
* investigación.

No púrpura brillante.

---

## Dental Clinic

Azul sanitario.

Representa:

* precisión;
* confianza;
* organización.

No colores hospitalarios excesivamente saturados.

---

# 54. Color Saturation

La saturación será moderada.

Nunca fluorescente.

Nunca pastel.

La prioridad será la legibilidad.

---

# 55. Contrast

Todos los banners deberán superar las recomendaciones WCAG para contraste entre:

* texto;
* fondo;
* elementos secundarios.

La accesibilidad tendrá prioridad sobre la estética.

---

# 56. Gradient Policy

Los degradados estarán permitidos únicamente cuando:

* sean muy suaves;
* refuercen la profundidad;
* no reduzcan la legibilidad.

Nunca serán protagonistas.

---

# 57. Typography Philosophy

La tipografía deberá transmitir:

* precisión;
* claridad;
* ingeniería.

No personalidad artística.

---

# 58. Font Family

Como GitHub controla la tipografía del README, el banner utilizará una familia sans-serif moderna que armonice con la interfaz.

El objetivo es que parezca una extensión natural de GitHub.

---

# 59. Typography Scale

Jerarquía recomendada.

| Element         | Relative Size |
| --------------- | ------------: |
| Project Name    |            XL |
| Tagline         |             L |
| Secondary Text  |             M |
| Decorative Text |  No utilizado |

---

# 60. Text Weight

El contraste tipográfico se conseguirá mediante:

* peso;
* tamaño;
* espacio.

No mediante color.

---

# 61. Text Alignment

La alineación oficial será:

```text id="visual003"
Left aligned
```

La alineación centrada solo se utilizará en casos excepcionales.

El contenido alineado a la izquierda facilita una lectura más rápida y mantiene coherencia con documentación técnica y herramientas de desarrollo.

---

# 62. Margins

Todos los banners compartirán una retícula de márgenes.

Zona segura.

```text id="visual004"
≈ 8% del ancho
```

Ningún elemento importante deberá acercarse a los bordes.

---

# 63. Grid System

La composición utilizará una retícula invisible.

Objetivos:

* alineación consistente;
* equilibrio;
* escalabilidad.

No será visible para el usuario.

---

# 64. Composition Zones

Cada banner tendrá cuatro áreas.

```text id="visual005"
Background Pattern

↓

Identity Zone

↓

Information Zone

↓

Whitespace
```

Cada una tendrá un peso claramente definido.

---

# 65. Identity Zone

Contendrá únicamente:

* nombre del proyecto;
* tagline.

Nada más.

No se añadirán iconos ni listas.

---

# 66. Information Zone

En el Profile Banner podrá incluir, si fuera necesario en futuras versiones:

* una frase muy breve.

En los banners de repositorios se evitará cualquier información adicional.

---

# 67. Pattern Zone

El patrón ocupará el fondo.

Nunca competirá con la zona de identidad.

---

# 68. Negative Space

El espacio negativo deberá representar aproximadamente un tercio del banner.

El objetivo es transmitir calma visual.

---

# 69. Balance

Todo banner deberá responder afirmativamente a esta pregunta.

```text id="visual006"
¿Podría eliminar un elemento sin perder información?
```

Si la respuesta es sí, probablemente ese elemento no debería existir.

---

# 70. Scalability

La composición deberá funcionar igualmente bien en:

* GitHub Banner;
* Social Preview;
* Open Graph;
* Slides;
* Documentación.

---

# 71. Responsive Behaviour

Aunque el banner sea una imagen estática, el contenido principal deberá permanecer legible cuando GitHub recorte ligeramente los extremos en distintos dispositivos.

---

# 72. Consistency Rules

No se modificarán entre proyectos:

* posición del título;
* márgenes;
* tamaño relativo;
* tipografía;
* estructura.

Solo cambiarán:

* nombre;
* color de acento;
* motivo gráfico.

---

# 73. Anti-Patterns

No utilizar:

* tipografías manuscritas;
* múltiples familias tipográficas;
* sombras exageradas;
* texto sobre patrones complejos;
* colores de acento múltiples;
* fondos fotográficos.

---

# 74. Quality Gates

Antes de aprobar un banner deberán verificarse:

* [ ] Contraste adecuado.
* [ ] Tipografía consistente.
* [ ] Márgenes respetados.
* [ ] Color de acento correcto.
* [ ] Legibilidad en modo claro.
* [ ] Legibilidad en modo oscuro.
* [ ] Composición equilibrada.
* [ ] Coherencia con el resto del ecosistema.

---

# 75. Part 3 Conclusions

El sistema cromático y tipográfico no busca crear una identidad llamativa.

Busca construir una identidad **coherente, sobria y fácilmente reconocible**.

La repetición consistente de colores de acento, composición y jerarquía tipográfica permitirá que todos los proyectos compartan una misma firma visual sin perder su personalidad propia.

La identidad gráfica deberá transmitir exactamente la misma sensación que el código y la documentación: orden, claridad y atención al detalle.

---

# 06 - BANNER

# Part 4/6

# Banner Architecture & Technical Specification

---

# 76. Purpose

Esta sección define la arquitectura técnica del sistema de banners.

Su objetivo consiste en garantizar que todos los activos gráficos del ecosistema GitHub puedan construirse siguiendo exactamente las mismas reglas.

El banner deja de considerarse una imagen aislada.

Pasa a ser un componente reutilizable.

---

# 77. Banner Architecture

Todos los banners compartirán la misma arquitectura.

```text id="bannerarch001"
Canvas

↓

Background

↓

Pattern Layer

↓

Accent Layer

↓

Identity Layer

↓

Export
```

Cada capa tendrá una única responsabilidad.

---

# 78. Layer Philosophy

Las capas no deberán mezclarse.

Cada modificación futura afectará únicamente a una capa.

Ejemplo.

Cambiar el color de un proyecto nunca implicará modificar:

* composición;
* tipografía;
* patrón principal.

---

# 79. Canvas Specification

Formato oficial.

```text id="bannerarch002"
1280 × 640 px
```

Relación:

```text id="bannerarch003"
2 : 1
```

Este formato permitirá generar fácilmente:

* GitHub Banner;
* Social Preview;
* Open Graph;
* documentación.

---

# 80. Export Formats

Formato maestro.

```text id="bannerarch004"
SVG
```

Derivados.

```text id="bannerarch005"
PNG

WEBP
```

Nunca se editará directamente un PNG.

El SVG constituirá el archivo fuente.

---

# 81. Source Files

Estructura propuesta.

```text id="bannerarch006"
assets/

banner/

profile/

projects/

patterns/

colors/

exports/
```

Todos los proyectos utilizarán esta organización.

---

# 82. Background Layer

Responsabilidad.

Crear profundidad.

Nunca información.

No contendrá:

* texto;
* iconos;
* logos.

---

# 83. Pattern Layer

Responsabilidad.

Representar la identidad conceptual del proyecto.

Nunca ilustrar literalmente su temática.

Ejemplo.

NovaCoquinaria.

↓

Knowledge Graph.

No:

platos.

ingredientes.

cubiertos.

---

# 84. Accent Layer

Responsabilidad.

Introducir la identidad cromática del proyecto.

Reglas.

* opacidad moderada;
* un único color;
* sin degradados agresivos.

---

# 85. Identity Layer

Única capa que contendrá información.

Componentes.

* nombre;
* tagline;
* opcionalmente una línea secundaria.

Nada más.

---

# 86. Safe Area

Todos los elementos importantes deberán permanecer dentro de una zona segura.

```text id="bannerarch007"
≈ 10% del perímetro
```

Esto evitará problemas de recorte.

---

# 87. Alignment Grid

La composición utilizará una retícula de:

```text id="bannerarch008"
12 columnas
```

No será visible.

Permitirá mantener coherencia entre banners.

---

# 88. Pattern Library

El sistema dispondrá de una biblioteca reutilizable.

Ejemplos.

```text id="bannerarch009"
GRID

GRAPH

LAYERS

FLOW

NETWORK

MATRIX
```

Cada patrón será parametrizable.

---

# 89. Pattern Reuse

Los patrones nunca pertenecerán a un único proyecto.

Serán componentes reutilizables.

Un proyecto nuevo únicamente seleccionará el patrón más adecuado.

---

# 90. Color Tokens

En lugar de colores escritos directamente.

Se utilizarán tokens.

Ejemplo.

```text id="bannerarch010"
PRIMARY

ACCENT

BACKGROUND

TEXT

MUTED
```

Esto facilitará futuros cambios.

---

# 91. Typography Tokens

Del mismo modo.

No se utilizarán tamaños absolutos.

Ejemplo.
